## 3. Security Review of SEB Middleware & Verification (Phase 0c)

### (i) Header Equivalence Vulnerability (`x-safeexambrowser-requesthash`)
In `backend/src/middleware/seb.js:216` and `backend/src/modules/seb/seb.controller.js:22`:
```javascript
const rawHeader = req.headers['x-safeexambrowser-configkeyhash'] || req.headers['x-safeexambrowser-requesthash']
```
- **Security Flaw**: `x-safeexambrowser-requesthash` is the legacy header for the **Browser Exam Key (BEK)** hash. Per SEB specification, BEK is generated from an entirely different secret (browser binary + config).
- **Remediation**: Purge `x-safeexambrowser-requesthash` entirely from Configuration Key checks. Accept ONLY `x-safeexambrowser-configkeyhash`.

### (ii) Verification of Starter Key & Candidate URLs Removal
- `STARTER_CONFIG_KEY` search: **0 matches** across `backend/src` and `backend/tests`. Completely removed.
- `candidateUrls` search: **0 matches**. Completely removed. The backend strictly evaluates one canonical URL: `${cleanPublicOrigin}${normalizedPath}`.

### (iii) Session Independence & Endpoint Gating (`markUserSebVerified`)
- `markUserSebVerified` was completely purged.
- In `backend/src/middleware/seb.js:232-234`:
  ```javascript
  // Passing the gate on HTTP routes strictly requires a valid header on that very request
  const isVerified = headerMatched
  ```
- Gated HTTP endpoints strictly verify the cryptographic header on every incoming request. A valid session cookie or prior launch token exchange cannot bypass gated routes.

### (iv) Enforce Mode Exchange Gating
- In `enforce` mode, both `exchange` and `exchangePin` strictly reject requests lacking a valid header with HTTP 403.
- In Phase 1, `exchangePin` will be refactored so that the PIN is validated first, but marked consumed ONLY AFTER the cryptographic header check succeeds.
